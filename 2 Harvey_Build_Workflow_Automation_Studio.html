Design ruleA Workflow agent is appropriate when the recurring task can be made explicit and reviewable. Automation should not turn legal, academic or assessment judgement into a tool-made decision.
1

Start with a recurring problem, not with automation.

Choose a task that genuinely recurs, can be expressed as explicit steps and has an output that a responsible person can check.

Use a Workflow agent when: the task has stable inputs, source boundaries, decision points, steps, outputs and review points. Keep final legal judgement, academic judgement, grading, misconduct findings and policy interpretation with authorised people.

Good fit

Repeatable and bounded

Seminar-question generation, authority checking, rubric mapping, case-teaching notes or updating defined unit materials.

Source control

Authoritative inputs

Specify judgments, legislation, rubrics, unit outlines, approved templates, Vault content or supported Knowledge Sources.

Human boundary

Visible review point

State what the educator or professional staff member must check before the output is used or shared.

!
Go / no-go test

If the workflow depends on unbounded discretion, an irreducible academic judgement, a final legal conclusion, or a decision that policy reserves for authorised staff, do not automate that decision. Reframe the agent around support, extraction, comparison, drafting or verification instead.

2

Specify the workflow before you build it.

The strongest build brief is an explicit specification of purpose, inputs, source boundaries, steps, decision points, output and human review—not simply a long prompt.

Specification

Make the workflow observable

Define what a successful run produces, what must be present before the agent proceeds, and what it should do when information is missing or contradictory.

Grounding

Do not leave sources implicit

Name the documents, Vaults or Knowledge Sources that should ground claims. Where source material is insufficient, require the agent to stop, ask or flag the limitation rather than widening the evidentiary base silently.

3

Build the Workflow agent in Agent Builder.

Harvey now uses Workflow agent for the reusable resource and Agent Builder for the current self-service creation environment. Some help material and interface elements still use Workflow Builder for the block-based editor.

i
Terminology matters

Treat Agent Builder and Workflow Builder as product/interface terms rather than different educational purposes. Published Workflow agents can be accessed through Library; ability to build, publish or run them depends on workspace permissions.

1
Open Agent Builder

From Build, open Agent Builder. In some workspace configurations you may also encounter Create from Library. If creation is unavailable, check Agent Builder access with the Harvey administrator.

2
Create a Workflow agent

Select Create Workflow agent. Depending on interface and permissions, Harvey may offer conversational Agent Builder and/or the block-based Workflow Builder experience.

3
Describe the workflow in natural language

Use Build with Harvey to describe the task, inputs, sequence, decision points, sources, output and review requirements. Use the design brief from the previous stage.

4
Add context and grounding

Attach or embed the documents, templates, Vaults or supported Knowledge Sources the agent should use. Make jurisdiction and source selection explicit where relevant.

5
Inspect generated steps

Review every generated block or instruction: ordering, assumptions, branching, required inputs, model choices, source settings, output labels and stopping points.

6
Configure the deliverable

Workflow agents can return structured responses and, depending on the build, can create or edit Word, PowerPoint and Excel files. Select only the output the workflow needs.

7
Save a clearly named draft

Use a name that identifies the task and audience, and keep a short version note while the agent is being tested.

4

Test the behaviour, not merely the happy path.

Start with public, dummy or otherwise low-risk materials. Verify the result, then deliberately test missing information, ambiguity, conflicting sources and out-of-scope requests.

Verification

Check against source or criterion

Verify factual claims, quotations, legal propositions, classifications, calculations performed elsewhere and pedagogical recommendations against the supplied sources, criteria or policy.

Boundary behaviour

Make failure modes visible

When inputs are incomplete or the task exceeds scope, the agent should stop, ask for clarification, flag uncertainty or escalate—not improvise.

!
Permissions are not pedagogy

Harvey sharing, approval and publication controls do not establish that a workflow is educationally appropriate. Before student use, separately check assessment design, academic integrity, privacy/data classification, accessibility, equity and local AI-use requirements.

5

Use agents where repeatability adds value without displacing judgement.

These examples are framed around bounded support tasks. The human decision identifies what the agent must not decide.

Case teaching

Case-teaching note

Turn a supplied judgment or verified case summary into a teaching note with material facts, issue, holding/reasons, questions and a source-checking step.

Human decision: educator verifies the legal account and decides what is taught.

Seminar preparation

Sequenced discussion questions

Generate staged questions from supplied materials, moving from comprehension to application and evaluation without automatically supplying model answers.

Human decision: educator sets the learning progression and decides which questions to use.

Authority checking

Claim-to-authority review

Compare claims in a draft teaching resource with supplied authorities and classify each as supported, incomplete, potentially misleading or unsupported.

Human decision: educator resolves legal meaning and decides amendments.

Assessment design

Assessment-design support

Map supplied ULOs, task instructions and criteria; produce a draft rubric structure, moderation checklist or assessment-design questions.

Human decision: academic staff approve standards, task validity and final criteria.

Feedback

Cohort feedback themes

Using permitted student data and a supplied rubric, identify patterns against criteria and draft cohort-level feedback themes for review.

Human decision: educator makes evaluative judgements and approves feedback.

Unit materials

Defined update review

Compare existing teaching material with a defined set of new authorities or policy documents and flag passages requiring review.

Human decision: educator determines whether and how content changes.

Worked example: seminar-question Workflow agent

Purpose: Support academic staff preparing seminar questions for an Australian law unit.

Inputs: Unit/topic, cohort level, jurisdiction, teaching aim, and a judgment extract, case summary or problem scenario.

Workflow: 1. Confirm the teaching aim. 2. Check the input is sufficient. 3. Identify the concepts students need to work with. 4. Generate five questions progressing from comprehension to application and evaluation. 5. Identify one likely misconception. 6. Add a source-checking prompt. 7. Finish with an educator review checklist.

Limits: Do not invent authorities. Do not assume facts not supplied. Do not produce model answers unless the educator explicitly selects a worked-example mode.

Output: A numbered question sequence plus misconception, source-checking prompt and educator review checklist.

6

Approve, version and share the agent deliberately.

A shared Workflow agent is a maintained educational resource. Record what it does, who owns it, what it may rely on, known limitations, how it was tested and what triggers review.

Model instruction for an educator-facing Workflow agent
Run purpose: Use this Workflow agent to support the stated teaching or educational-design task. Treat its output as a draft or analysis for review, not as legal authority or an automated academic decision.

Source use: Where the workflow relies on a supplied judgment, statute, policy, rubric or Knowledge Source, check material propositions against that source before use.

Uncertainty: If an input is missing, the jurisdiction is unclear, or the source material does not support a requested conclusion, flag the limitation rather than filling the gap.

Assessment judgement: Do not allow the workflow to determine a final grade, progression decision, misconduct finding or other decision reserved for authorised staff.

Data: Use student, confidential or sensitive material only where the relevant institutional rules and the configured Harvey environment permit it; otherwise use de-identified, dummy or public material.

Responsibility: The educator remains responsible for what is accepted, revised, rejected, shared with students and incorporated into teaching or assessment.

Key validity corrections from the May 2026 resource
  • Terminology: “Workflow Automation / Build” is replaced as the main label by Workflow agents and Agent Builder; Workflow Builder remains relevant to the block editor.
  • Build method: the former “editable narrative-based agent” description is replaced by natural-language Build with Harvey plus editable block-based workflow design.
  • Grounding: custom workflows can use embedded Vaults and supported Knowledge Sources, not uploads alone.
  • Outputs: current custom Workflow agents can create or edit Word, PowerPoint and Excel files where supported.
  • Sharing: generic colleague sharing is replaced with Run, View, Edit and Full access levels plus approval/publication.
  • Data governance: the guide does not present Harvey itself as universally prohibiting confidential, privileged or personally identifiable material; users must follow institutional and workspace rules.
