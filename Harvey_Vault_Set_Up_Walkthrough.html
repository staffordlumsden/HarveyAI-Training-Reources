Design ruleA well-designed Vault is a governed source environment: purpose → permitted corpus → controlled access → bounded query → source verification → educator judgement → periodic maintenance.
1

Choose the right starting point.

Use Vault when persistence, scale or reuse adds real value. For a one-off task involving only a few files, Assistant is usually simpler.

Vault supports document organisation and analysis; it does not replace legal judgement, source verification, educator review or University data-governance requirements. The key question is whether the task needs a persistent, governed corpus for the people who will use it.

Assistant

Small, one-off task

Upload a few relevant files or select approved sources and run a bounded question, comparison or draft.

Vault

Persistent corpus

Use for a case set, teaching-source collection, verified precedents or another large permitted document set that will be reused.

Review Table

Same questions, many files

Create independently or from a Vault when you need structured extraction or comparison across documents.

Workflow agent

Repeatable process

Define steps, limits, sources and human review points. It is a reusable process, not a document store.

!
Do not collapse product functions.

A Vault is not automatically a Knowledge Source, Review Table or Workflow. Treat the Vault as the governed corpus and choose the analysis or workflow feature separately.

2

Plan and govern the corpus before uploading.

Define the purpose, data boundary, access model and maintenance responsibility before creating the Vault. Security features do not decide whether a University document is permitted.

1
Define the educational purpose.

Keep the purpose narrow enough that you can explain what belongs in the corpus and what does not.

2
Confirm the data boundary.

Check University data classification, privacy, assessment, copyright/licensing and AI-use requirements for the proposed documents.

3
Minimise identifiers and sensitive content.

Remove unnecessary names, student IDs, email addresses, comments, coversheets and metadata unless retention is explicitly authorised.

4
Curate rather than accumulate.

Upload only documents relevant to the task. A bounded corpus is easier to verify, maintain and explain.

5
Use a naming convention.

Name the Vault so its scope is obvious: [UNIT / PROJECT] – [TOPIC / CORPUS] – [PERIOD / VERSION].

6
Assign a maintenance owner.

Decide who adds, replaces or removes documents and how superseded material will be handled.

7
Set the sharing boundary before sharing.

Shared Vault access can expose files and query history. If an output is sufficient, share/export the output instead of the corpus.

8
Define review and retention triggers.

Use semester rollover, major legal change, a new source edition, project completion or local policy change as practical review points.

i
Security and governance are separate questions.

Harvey states that customer inputs, outputs and uploaded documents are not used to train underlying models and offers in-region processing, including Australia. Those safeguards do not replace University decisions about whether material may be uploaded, shared, retained or used for assessment-related purposes.

Suggested Vault name
[UNIT / PROJECT] – [TOPIC / CORPUS] – [PERIOD / VERSION]

3

Create and orient the Vault.

Do not begin with substantive legal analysis. First confirm that the intended corpus has uploaded, processed and can be retrieved reliably.

1
Create the Vault.

Use the approved name and purpose. Keep unrelated projects separate where access, retention or source rules differ.

2
Add supported source documents.

Use meaningful filenames that distinguish court, year, version or source. Use approved integrations only where enabled for your workspace.

3
Allow processing to finish.

Resolve failed or unreadable files before relying on queries across the corpus.

4
Run a corpus-orientation check.

List document types, duplicates, obvious outliers and files that cannot be read confidently.

5
Test source retrieval.

Ask a narrow factual question whose answer you already know and confirm the intended source is retrieved.

6
Extract before interpreting.

First extract identifiable features such as case, court, issue, provision and paragraph; then move to comparison or synthesis.

7
Reuse the Vault deliberately.

Vault content can be used across Harvey, including Assistant and Workflows. Add other sources only when the task genuinely requires them.

Initial corpus-check prompt
Instruction: Using only the documents in this Vault, produce a corpus inventory before doing legal analysis.

For each file, identify:
- document/file name;
- apparent document type;
- court/source and year where evident;
- jurisdiction;
- whether the file appears complete/readable; and
- whether it appears relevant to [TASK].

Checks: Flag apparent duplicates, superseded versions, documents outside the stated jurisdiction or period, and any file whose content is uncertain. Do not infer missing metadata.

Output: A concise table followed by “Corpus issues requiring educator review”.
4

Query, compare and verify.

A bounded Vault improves source control, but it does not make every generated statement correct. Keep source scope, task boundaries, evidence requirements and human checking visible.

Source scope

State the boundary

Specify whether Harvey must use only the Vault or may combine it with another approved source.

Jurisdiction + period

Prevent drift

Name the legal system, court level and date range relevant to the task.

Task boundary

Separate operations

Keep extraction, comparison, synthesis, drafting and teaching design distinct where possible.

Evidence

Make checking faster

Request source references for material legal claims and require uncertainty to be identified.

Legal currency

Check outside the Vault

Use an approved current legal database or Knowledge Source when authority status, subsequent treatment or currency matters.

Human decision

Record acceptance or correction

Document what the educator accepts, changes or rejects before student-facing use.

!
“Using only this Vault” is a source-scope instruction, not a currency guarantee.

A corpus can be internally coherent and still be legally out of date or incomplete.

Case comparison prompt
Instruction: Using only the judgments in [VAULT NAME], compare the treatment of [LEGAL ISSUE] for [COHORT / TEACHING PURPOSE].

For each judgment:
- identify procedural posture;
- precise issue;
- outcome/holding;
- principal reasoning;
- relevant statutory provision(s); and
- source paragraph(s).

Comparison: Identify genuine points of convergence or divergence only where supported by the judgments. Distinguish a difference in facts from a difference in legal principle.

Limits: Do not infer subsequent treatment, current authority or external doctrine from the Vault alone. Flag any proposition that needs checking against an approved current legal database.

Output:
1. comparison table;
2. three teaching points;
3. matters requiring educator verification.
5

Use Review Tables for structured analysis across documents.

Use a Review Table when the same structured questions need to be answered across many files. Current Harvey supports both independent Review Tables and Review Tables created from a Vault.

Current scale

Vault-backed table

Current guidance allows up to 10,000 Vault files in a Review Table.

Direct upload

Independent table

Direct desktop uploads are currently limited to 50 files. The reviewed set comes from one source context rather than mixing multiple Vaults and uploads.

1
Choose the source context.

Use direct upload for a small bounded set; use the relevant Vault for a large or persistent corpus.

2
Design columns around the question.

Prefer precise fields such as issue, provision, authority, reasoning evidence, omission, teaching point and verification status.

3
Separate extraction from evaluation.

Extract relatively factual items first; place evaluative judgements in later columns tied to explicit criteria or verified data.

4
Use conditional columns deliberately.

Verify upstream columns before relying on downstream conditional analysis.

5
Inspect reasoning and citations.

Current Review Tables provide transparent reasoning and sentence-level source links; click through and verify material cells.

6
Correct and annotate.

Use editing, comments, verification/activity features or manual-input columns where available to preserve the human-review layer.

7
Ask over the verified table.

Use the populated table for synthesis or a teaching/moderation brief. A Review Table can also be reused as a Knowledge Source.

6

Share the corpus only when corpus-level access is intended.

Shared Vault access can expose files and query history, while higher permissions can permit editing or sharing changes. If a recipient needs only the result, share or export the result.

Key currency and validity corrections from the May 2026 guide
  • When to use Vault: one-off work with a few files can usually begin in Assistant; Vault is positioned for persistent/high-volume review.
  • Scale: current product information states up to 100,000 documents per Vault.
  • Cross-platform use: Vaults can be reused across Harvey, including Assistant and Workflows.
  • Review Tables: they can be created independently from direct uploads or from a Vault; current limits are 50 direct uploads or up to 10,000 Vault files.
  • Citations: sentence-level citations and reasoning aid validation but do not remove human source checking.
  • Sharing: shared Vault access may expose files and query history.
  • PII/confidentiality: Harvey's enterprise security commitments do not determine what University material may be uploaded.
  • Currency: a bounded Vault may be internally coherent and still legally out of date.

Validity check: the August 2026 source guide records checks against Harvey's Vault product overview, Getting Started guidance, Vault Help Centre material, Review Tables guidance, advanced Vault controls, sharing/uploading guidance and Harvey Security. Functionality can vary by region, workspace configuration, permissions and release timing.
